# comb-the-desert v0.5.0 — design spec

**Status:** Approved 2026-05-05 (brainstorming session)
**Trigger:** A real `/comb:the-desert` run on a tero-app branch surfaced three structural issues that needed coherent treatment, not point fixes. The transcript showed: G4 implementer refusing to write (read-only agent), G6 escalating, G8 applied inline by the orchestrator with no documented authorization, 2/9 plan agents returning content inline instead of writing, and 21 modified + 4 deleted files left uncommitted at run end.
**Predecessor:** v0.4.3

---

## 1. Goal

Fix the structural issues that prevent `/comb:fix` and `/comb:the-desert` from completing without orchestrator workarounds. Bring the dispatch model closer to the proven plan→implement→verify pattern from superpowers while preserving comb's specialty-driven review model and config flexibility. All changes additive at the config layer (no migration required).

---

## 2. Approved design decisions

1. **Writer-capable agent for fix/plan dispatch.** Add `agents.implementer` to `config/defaults.json`, defaulting to `general-purpose`. Fix Step 4d (implementer) and plan Step 6 (plan-file writer) dispatch through `agents.implementer`. The five `comb:*` review agents stay read-only (`disallowedTools` intact).

2. **Per-item commits default-on, opt-out via `fix.commit_per_item`.** The orchestrator (not the implementer) runs the commit on PASS with message `<finding-code>: <title>`. A pre-flight check warns once if the working tree is dirty before the run starts. In `/comb:the-desert`, the question is suppressed when the tree is clean (preserves the no-pause contract).

3. **Plan files use ADR-style alternatives.** The main body remains the single executable path. An optional `## Considered alternatives` section at the end documents rejected approaches with one-line "rejected because" rationale. No "Decision required" gates in plans; planners commit to one path.

4. **Planner-quality nudge.** The planner dispatch prompt asks the planner to trace through proposed fix's failure modes before recommending — particularly when correctness depends on a runtime invariant (closure state, async timing, render scheduling, lifecycle ordering, transaction isolation).

5. **Orchestrator-as-implementer escape hatch.** Documented: after 3 implementer failures *and* the item is classified trivial (per Step 4c), the orchestrator may apply the fix inline. The reviewer step still runs against the inline change. Standard items that hit 3 failures escalate to the user as before.

6. **Specialty-matched fix-reviewer.** The agent that flagged the original finding reviews the fix — not test-auditor by default. Plan files gain a `**Specialty:**` line in the header block carrying the source-agent info from the review report. Reviewer dispatch resolves the specialty from this line.

7. **Reviewer's role is strict plan-compliance.** Reframe the reviewer's prompt around plan-as-spec: did the implementation execute the plan? What diverged, and is the divergence justified? The implementer must explicitly report any divergences with rationale; the reviewer evaluates each rationale rather than re-litigating the fix's design.

## 3. Config schema additions

`config/defaults.json` gains:

```json
{
  "agents": {
    "...existing five comb:* roles unchanged...": "...",
    "implementer": {
      "subagent_type": "general-purpose",
      "when_to_use": "Default writer-capable agent for /comb:fix and /comb:plan. Full tool access. Override per-project to plug in a specialist writer."
    }
  },
  "fix": {
    "commit_per_item": true
  }
}
```

`models.fix.implementer_trivial` and `models.fix.implementer_standard` continue to drive model selection at dispatch time; `agents.implementer` controls which `subagent_type` executes. User configs that omit either field inherit the default via deep-merge. No migration required.

## 4. Skill body changes

### 4.1 `skills/fix/SKILL.md`

**Step 1 (Load config).** Read the new `agents.implementer` and `fix.commit_per_item` keys alongside existing config.

**New Step 1.5 — Pre-flight check.**
- Run `git status --porcelain`. If the tree is clean, proceed.
- If dirty, surface a one-shot question with four options: (a) commit existing changes now, (b) stash and restore at run end, (c) proceed without per-item commits for this run, (d) abort.
- In `/comb:the-desert`, suppress the question when the tree is clean. If dirty in the-desert, ask once at the start (this is the only allowed question beyond scope).
- Skip the entire pre-flight if `fix.commit_per_item: false`.

**Step 4d (Send to implementer).**
- Picker default changes from `code-reviewer` to `agents.implementer`.
- Resolve `subagent_type` from `agents.implementer.subagent_type` (default `general-purpose`).
- Resolve model from `models.fix.implementer_standard` (or `_trivial` per Step 4c classification).
- Add to the dispatch prompt:
  > **Reporting divergences.** If you must deviate from any step in the instruction's How section, list the deviation under a `## Divergences` heading in your reply with a one-line rationale per deviation. If you executed the instruction as written, omit the heading. The reviewer reads your divergences and evaluates each rationale — being explicit is how the run stays honest.

**Step 4e (Send to reviewer).**
- Resolve `subagent_type` from the plan file's `**Specialty:**` header. The header lists one or more source agents (e.g., `code-reviewer`, `code-reviewer + consistency-auditor`). The orchestrator picks one based on the finding's primary lens.
- Fallback chain when the header is missing or the resolved subagent_type isn't in the user's `agents` config: `agents.test-auditor` → `agents.code-reviewer`.
- Reframe the dispatch prompt around plan-compliance:
  > Your job is to verify the implementation executed the plan. The plan file is the contract. Read the plan, read the implementer's report (including any `## Divergences` section), then read the actual diff via `git diff HEAD~1 -- <files>` (per-item commit) or `git diff -- <files>` against the implementer's reported file list (no-commit mode).
  > 
  > **Decision rule:**
  > - **PASS** — every step of the plan's How section is reflected in the diff, OR each divergence reported by the implementer has a sound rationale, AND the Expected Outcome is achieved.
  > - **FAIL** — the diff doesn't match the plan and no rationale was given, OR the rationale doesn't justify the deviation, OR the Expected Outcome isn't achieved, OR the diff includes changes outside the plan's Scope.
  > 
  > You are not auditing for general code quality. The plan is the spec. Stay narrow.

**Step 4f.1 — Commit on PASS (new).**
```
If fix.commit_per_item is true and the item produced code changes:
  git add <files reported by implementer>
  git commit -m "<finding-code>: <title>"

  On commit failure (hooks fail, conflicts, signing): abort the run, surface the error and the affected item's code.
```

When `fix.commit_per_item` is false, skip the commit entirely. The implementer's changes accumulate in the working tree (legacy v0.4.x behavior).

**Step 4g — Trivial escape hatch (new).**
> If an item has failed 3 times *and* was classified trivial at Step 4c, the orchestrator may apply the fix inline rather than re-dispatch a fourth implementer. The reviewer step (4e) still runs against the inline change. Standard items that hit 3 failures escalate to the user as before. The orchestrator must announce the escape:
> ```
> {code} — escape: orchestrator applying inline (3 implementer failures, trivial item)
> ```

**Top-of-skill clarification.** Add a note that the implementer is no longer one of the `comb:*` review agents; it's `agents.implementer` (default `general-purpose`).

### 4.2 `skills/plan/SKILL.md`

**Step 6 (Send one agent per finding or group).**
- Resolve `subagent_type` from `agents.implementer` (not `agents.<role>`). The "specialist per finding" picker for *implementation* of the plan file is gone — but the planner dispatch still picks a specialty lens to frame the prompt (e.g., "approach this finding as a `simplifier`"). The lens informs the planner; the writer is `agents.implementer`.
- Add the planner-quality nudge to the dispatch prompt:
  > Before recommending a fix, trace through its failure modes. If correctness depends on a runtime invariant — closure state, async timing, render scheduling, lifecycle ordering, transaction isolation — simulate the failure path mentally and confirm the proposed fix breaks it. If you cannot, surface the structural concern in your output rather than recommend a flawed fix.

**Step 6 output format — header block gains `**Specialty:**`.**

Updated header shape:

```markdown
# {reference_code} — {one-line title}

**Severity:** {Critical | High | Medium | Low | Test gap | Deferred}
**File(s):** {paths with line ranges}
**Specialty:** {source agent(s) from review report — comma-separated if multiple}
**Consolidates:** {comma-separated finding codes — for grouped findings only}
```

The `**Specialty:**` value comes from the review report's `*Source: <agent>*` line for that finding. For grouped findings, list the union of source agents from the consolidated findings.

**Step 6 output format — optional `## Considered alternatives` section.**

Placed after `## Directive citations`. Format:

```markdown
## Considered alternatives

- **<Alternative title>** — Rejected because <one-line rationale>
- ...
```

The main body of the plan still represents a single executable path. The alternatives section is documentation, not a decision gate.

### 4.3 `skills/the-desert/SKILL.md`

Two small touch-ups:

- **Update the "Only questions" rule.** The current rule says: "scope at the start (if ambiguous), and 'run again?' at the end." Add: "and the dirty-tree pre-flight question if the working tree is dirty when the sweep begins (clean tree → no question)." This keeps the no-pause contract intact for the common case while honoring the safety check.
- **Step 5 (Run fix) inherits commit behavior.** Add a one-line note: "Per-item commits per `fix.commit_per_item` (default true) apply during the desert sweep. The `models.the_desert` coercion governs subagent models; commit behavior is unaffected."

### 4.4 `skills/help/SKILL.md`

Update the `/comb:fix` per-command entry:
- Add: "Pre-flight check on dirty working tree."
- Add: "Per-item commits with `<code>: <title>` message; opt-out via `fix.commit_per_item: false`."
- Already mentions "Per-item commit, with the finding code + title in the message" — this becomes truthful in v0.5.0.

## 5. Plan-file format reference (v0.5.0)

```markdown
# {reference_code} — {one-line title}

**Severity:** {Critical | High | Medium | Low | Test gap | Deferred}
**File(s):** {paths with line ranges}
**Specialty:** {source agent(s) from review report}
**Consolidates:** {comma-separated finding codes}   ← for grouped findings only

---

## What
## Why
## Where
## How
## Expected Outcome
## Scope
## Directive citations
## Considered alternatives                            ← optional
```

The `**Specialty:**` and `## Considered alternatives` are the only changes from v0.4.x.

## 6. Implementer & reviewer prompt deltas (summary)

**Implementer dispatch (v0.5.0 additions):**
- `## Divergences` reporting requirement.

**Reviewer dispatch (v0.5.0 reframing):**
- Plan-compliance is the verdict, not general code quality.
- Read implementer's `## Divergences` section before reading the diff.
- Use `git diff HEAD~1 -- <files>` when `commit_per_item` is on; falls back to file-list-scoped working-tree diff otherwise.

**Planner dispatch (v0.5.0 addition):**
- Failure-mode trace-through nudge.

## 7. Migration & backward compatibility

- All changes are additive at the config layer. Existing `comb.config.json` files in user projects inherit `agents.implementer` and `fix.commit_per_item` defaults via deep-merge.
- The five `comb:*` review agents are not modified. Their `disallowedTools` stays.
- Users who explicitly mapped `agents.<role>.subagent_type: "general-purpose"` as a workaround for the v0.4.x bug continue to work but should remove the override after upgrade — the new default kicks in cleanly.
- `models.fix.implementer_*` keys are unchanged.
- Users who liked the v0.4.x no-commits behavior set `fix.commit_per_item: false` in their config. **Trade-off documented:** with commits off, the reviewer can't `git diff HEAD~1 -- <files>`. The fallback (`git diff -- <files>`) shows all accumulated changes to those files since HEAD, reintroducing the cumulative-diff false-positive risk that motivated this release. Users opting out accept this.

---

## 8. Out of scope (future consideration)

- **Two-stage review** (spec compliance → code quality). Superpowers does this; comb stays single-stage to keep dispatch counts reasonable at our typical scale (often 9–25 items per run). Revisit if v0.5.0's reviewer false-positive rate is high.
- **Implementer exit codes** (`DONE`, `DONE_WITH_CONCERNS`, `NEEDS_CONTEXT`, `BLOCKED`). The 3-failure rule + escape hatch + new `## Divergences` reporting cover the same ground for now.
- **Branded `comb:implementer` shipped agent.** Not needed — `general-purpose` is sufficient. If we want opinionated implementer guidance later, we can add a shipped agent without changing the config schema.

---

## 9. Verification plan

Verification for v0.5.0 is informal (there are no automated tests for skill behavior). The release is verified by running `/comb:the-desert` against a known repository and confirming:

1. No "agent self-identified read-only" failures in fix or plan dispatch.
2. Working tree is clean after a successful sweep — every item that PASSed has a corresponding `<code>: <title>` commit.
3. Reviewer dispatches show specialty matching — the agent reviewing each finding is one of the original review agents named in the plan's `**Specialty:**` header, not always test-auditor.
4. A planner that produces a `## Considered alternatives` section is rendered correctly in the plan file (no template rejection).
5. A trivial item that fails 3× is applied by the orchestrator inline and still goes through the reviewer.
6. `fix.commit_per_item: false` in a user config reproduces v0.4.x behavior (no commits).

## 10. Implementation strategy (handoff to writing-plans)

Suggested ordering:

1. **Config schema** (`config/defaults.json`) — additive, low-risk, unblocks downstream changes.
2. **Plan SKILL changes** — header `**Specialty:**`, alternatives section, planner nudge, dispatch via `agents.implementer`. Plan changes are upstream of fix's reviewer-resolution logic.
3. **Fix SKILL changes** — biggest body of work: pre-flight check, dispatch via `agents.implementer`, divergences in implementer prompt, plan-compliance reviewer prompt, commit-on-PASS, escape hatch.
4. **The-desert SKILL & help SKILL** — small documentation touch-ups.
5. **README, CHANGELOG, plugin.json** — version bump to 0.5.0, document the behavior change prominently in CHANGELOG (this is not a patch-level release).
6. **Smoke test** against a real branch (your tero-app fork is the obvious choice — re-running `/comb:the-desert` against the same scope should produce a clean working tree at the end).
